Skill 优化记录

项目：韩老魔大婚记 (6集 H3 视频制作)
日期：2026-09-12
涉及 Skill：runninghub-video-production / h3-prompt-writing / h3-drama-producer
本次制作概要：6 集 15s H3 视频经多轮迭代完成，累计发现 5 类 API 问题 + 4 类 Prompt 工程问题 + 2 类工作流问题，以下逐条记录并给出 Skill 改进建议。

一、runninghub-video-production API 文档

1. 图片上传端点冲突（已修复，需文档强化）

问题：存在两个上传端点，返回路径前缀不同：

  • 旧端点 /task/openapi/upload → 返回 api/<hash>.png
  • v2 端点 /openapi/v2/media/upload/binary → 返回 openapi/<hash>.png

t8lite v2 App API 仅接受 openapi/ 前缀。用旧端点上传后做字符串替换 api/ → openapi/ 无效，因为文件物理存储位置不同。

建议：SKILL.md 中已在 Image Upload 章节记录了 v2 端点，但应增加 红色警告："禁止使用旧端点 /task/openapi/upload，其返回的 api/ 路径不兼容 t8lite v2 API。所有上传必须使用 /openapi/v2/media/upload/binary。"

2. query 响应字段名为 results（已在文档中，但实战踩坑）

问题：查询 API 返回的视频 URL 在 results 列表中，不是 result.outputs。第一版轮询脚本用了 resp.get("result", {}).get("outputs", []) 导致下载失败。

建议：SKILL.md 已正确记录此格式。可以在 Troubleshooting 章节增加一个常见错误案例："如果脚本返回 SUCCESS 但未下载到视频，检查是否用了 result.outputs 而非 results。"

3. usage 字段可能为 None

问题：resp.get("usage", {}) 在 API 返回 "usage": null 时返回 None（不是 {}），导致 NoneType.get() 报错。

建议：在 SKILL.md 的代码示例中统一使用 resp.get("usage") or {} 模式，并注明原因。

4. duration 参数支持非 15 秒值

问题：nodeId 27 的 fieldValue 通常设为 "15"，但实测 "17" 也能正常生成。17s 视频耗时约 547s（vs 15s 约 410s），费用略增。

建议：SKILL.md 中 nodeId 表格注明"支持值范围：5-17（需验证上限）"，并添加一行："'15' 为标准时长，'17' 已验证可用，非标准时长会增加生成时间和费用。"

5. ffmpeg 可能被编译为精简版

问题：系统中内置的 ffmpeg 可能以 --disable-everything 编译，不支持 PNG 编码。帧提取需要用 Python cv2 替代。

建议：在 SKILL.md 的 Troubleshooting 增加："如需从视频提取帧，优先使用 Python OpenCV (cv2.VideoCapture) 而非 ffmpeg，因内置 ffmpeg 可能缺少编码器。"

二、h3-prompt-writing Prompt 工程

6. 人物克隆/复制问题（高频，需模板化）

问题：AI 视频模型在广角多人镜头中极易将同一角色复制多次（如 E05/E06 出现两个韩立、E03 韩立背后出现虚化人影）。

验证有效的反克隆写法：

CRITICAL ANTI-CLONING RULE: Each character appears ONLY ONCE in every frame.
NO character is duplicated, cloned, multiplied, or appears multiple times
in the same shot. There is exactly ONE [Character A], ONE [Character B]...
in any given frame. If multiple characters appear in a shot, they are all
distinct individuals standing in different positions - never the same
person twice.

需在 summary、detailed_description 开头、retention_analysis 每条末尾三处重复。

建议：在 references/ref-en.txt 中增加 "Anti-Cloning Clause" 标准模板段落，作为多人场景的必选子句。

7. 台词串台 / 说话人归属错误

问题：角色 A 的台词在画面切换到角色 B 的镜头时，模型让角色 B 继续说了角色 A 的剩余台词。如 E03 中紫灵的台词被南宫婉"接话"。

验证有效的修复策略：

  • 说话角色在说台词的镜头中必须 可见且居中，添加 "her lips visibly move"
  • 非说话角色在 subject_definitions 中标注 "She does NOT speak any dialogue in this episode"
  • 每个镜头末尾加注 "NOTE: Only [Speaker] (S1) speaks in this shot. [Non-speaker] does NOT speak."
  • 避免在说话角色的台词镜头后紧接切到另一角色特写——改用广角让说话角色仍在画面内

建议：在 ref-en.txt 的 dialogue 部分增加 "Speaker Attribution Rules" 子段落。

8. 角色离场后残留 / 背景虚化人影

问题：角色在 Shot 1 变身/飞走后，后续镜头仍出现该角色身影或背景中生成类似该角色的虚化人影。如 E06 中韩立已化光飞走，Shot 2 仍出现两个韩立。

验证有效的修复写法：

# subject_definitions 中：
 ... He appears ONLY in [Shot 1]...
After [Shot 1], his physical body is COMPLETELY GONE from the platform
- no trace of his figure, body, silhouette, or duplicate remains.

# detailed_description 中新增独立规则段：
CRITICAL HAN LI ABSENCE RULE: After [Shot 1], Han Li's physical body
is COMPLETELY GONE. There is NO figure, body, silhouette, ghost,
afterimage, or duplicate visible in [Shot 2] through [Shot 6].
The space where he stood is EMPTY.

# 具体镜头中：
[Shot 2] ... the platform where Han Li stood is now EMPTY...
NO Han Li figure visible on the platform.

建议：在 ref-en.txt 增加 "Character Absence Management" 段落，覆盖变身/飞走/消失等仙侠常见场景。

9. 背景人物生成不受控

问题：角色背后可能出现不属于剧本的虚化人影，且该人影可能酷似主角（如 E03 中韩立背后出现类韩立人影）。

验证有效的写法：

Behind him is ONLY the white jade plaza floor, jade pillars,
and spiritual clouds - absolutely NO duplicate, ghost, silhouette,
or blurred figure of any kind appears behind him at any point.

需在 subject_definitions 的角色定义中、以及每个该角色出现的镜头描述中重复。

建议：在 ref-en.txt 增加 "Background Control" 子段落，提供标准禁止性描述模板。

三、h3-drama-producer 工作流

10. 跨集场景一致性：从 E01 提取环境参考帧

问题：E01-E02 生成的白玉广场环境在 E05/E06 中出现了场景不一致（时间/光照/布局差异）。

验证有效的方案：

  • 用 Python cv2.VideoCapture 从 E01 视频第 1 秒提取全景帧
  • 将该帧上传为额外图片参考 (<Picture N>)，在 subject_definitions 中定义 <Subject N> is the [environment] from <Picture N>
  • 在 detailed_description 开头声明 "The environment must match <Picture N>"
  • 在 retention_analysis 中为环境 Subject 添加 fully_preserved 条目

建议：在 h3-drama-producer 的工作流步骤中增加 "环境参考帧提取" 步骤，位于"首轮视频生成"之后、"后续集数提交"之前。作为分集制作的标准操作。

11. 迭代修复工作流标准化

问题：用户审片后提出多个具体问题（场景不一致、台词串台、人物克隆、角色残留），需要逐个修改 prompt 重制。当前没有标准化的迭代流程。

建议的迭代修复流程：

  1. 问题分类：将用户反馈分为 Prompt 问题（场景/台词/克隆/残留）和 API 问题（路径/格式/超时）
  2. Prompt 修改：针对每类问题应用对应模板（反克隆子句、说话人归属规则、角色缺席规则、背景控制子句）
  3. 图片复用：已上传的 openapi/ 路径在 24h 内可直接复用，无需重新上传
  4. 版本管理：payload 文件命名加版本号（如 t8lite-E06v3-payload.json），视频文件同步
  5. 单集提交：修复版单独提交，不批量（便于快速验证）
  6. 结果对比：新旧版本并排存放，方便用户对比效果

建议：在 h3-drama-producer 的工作流末尾增加 "迭代修复" 章节，包含上述流程和常见问题→模板映射表。
